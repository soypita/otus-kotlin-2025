# Нефункциональные требования

### 1. Производительность

1.1. **Время ответа сервера (API)**
    - **Источник требования:** Разработчик, Пользователь.
    - **Описание требования:** Система должна быстро обрабатывать запросы пользователя на создание, чтение и обновление записей о книгах.
    - **Параметры:** Среднее время обработки CRUD-запросов на сервере не должно превышать **200 миллисекунд** (без учета сетевой задержки).
    - **Приоритет требования:** Высокий.

1.2. **Производительность real-time обновлений (в будущем)**
    - **Источник требования:** Разработчик.
    - **Описание требования:** При реализации социального функционала, доставка уведомлений клиентам должна происходить с минимальной задержкой.
    - **Параметры:** Задержка доставки сообщения от сервера до клиента не должна превышать **500 миллисекунд**.
    - **Приоритет требования:** Средний (для будущих этапов).

### 2. Надежность

2.1. **Доступность сервиса**
    - **Источник требования:** Разработчик, Пользователь.
    - **Описание требования:** Сервис должен быть доступен для использования. Для учебного проекта это означает отсутствие критических ошибок, приводящих к постоянным падениям приложения.
    - **Параметры:** Доступность сервиса на уровне **99.9%**. Допускаются короткие простои для обновления и обслуживания.
    - **Приоритет требования:** Высокий.

2.2. **Сохранность данных**
    - **Источник требования:** Пользователь.
    - **Описание требования:** Данные, введенные пользователем (список книг, оценки, отзывы), не должны теряться в результате сбоев.
    - **Параметры:** Использование персистентной базы данных с настроенным механизмом резервного копирования (в промышленной эксплуатации).
    - **Приоритет требования:** Высокий.

### 3. Безопасность

3.1. **Изоляция данных пользователей (в будущем)**
    - **Источник требования:** Пользователь.
    - **Описание требования:** Пользователь должен иметь доступ только к своим записям о книгах.
    - **Параметры:** Все запросы к API должны проверять принадлежность запрашиваемых или изменяемых данных текущему аутентифицированному пользователю.
    - **Приоритет требования:** Высокий (при введении системы пользователей).

### 4. Масштабируемость

4.1. **Масштабируемость бизнес-логики**
    - **Источник требования:** Разработчик.
    - **Описание требования:** Архитектура должна позволять обрабатывать растущее количество запросов. В контексте проекта это означает использование асинхронного подхода.
    - **Параметры:** Приложение должно эффективно утилизировать ресурсы CPU и памяти, не создавая блокировок на потоках.
    - **Приоритет требования:** Средний.

4.2. **Масштабируемость через шину событий (в будущем)**
    - **Источник требования:** Разработчик.
    - **Описание требования:** Использование шины событий позволит в будущем добавлять новые микросервисы (рекомендации, нотификации) без изменения основного приложения, что обеспечивает горизонтальное масштабирование системы.
    - **Приоритет требования:** Средний.

### 5. Поддерживаемость

5.1. **Качество кода**
    - **Источник требования:** Разработчик, Ментор курса.
    - **Описание требования:** Код должен быть чистым, хорошо структурированным и следовать общепринятым соглашениям.
    - **Параметры:** Логика должна быть разделена на слои (API, бизнес-логика, доступ к данным). Наличие юнит-тестов для бизнес-логики.
    - **Приоритет требования:** Высокий.
